# Moving the TTRPG GM stack to the Bmax B1 Pro

Prepared 2026-11-18. Target: a dedicated, always-on AI Game Master machine.
Source: this MacBook Air, which keeps working as client and cold backup until
the mini PC has proven itself.

## Verdict first

The B1 Pro will run this stack, and it is the floor, not the sweet spot.

- **CPU:** Celeron N4000, 2 cores and 2 threads. All model inference is remote
  (OpenRouter), so the CPU only serves Foundry's Node process, the Hermes
  gateway, and the Python tooling. That is enough for one player. World loads
  and journal searches will be noticeably slower than on the M1.
- **RAM:** 8 GB LPDDR4, soldered, not upgradable. Enough for Foundry, the
  gateway, the bridge, and the memory store if the machine stays headless. Do
  not also run the browser, SearXNG, or camofox there.
- **Storage:** 128 GB eMMC, slow and finite. The slot is **M.2 2280 SATA3**,
  not NVMe. Buy a SATA M.2 SSD, up to 2 TB, and put the OS, Foundry data, and
  backups on it. Do not buy an NVMe drive.
- **Network:** Gigabit Ethernet. Use the cable, not Wi-Fi 5.
- **Power:** 12 V, 24 W supply, fanless in most units. Good always-on box.

If the machine has not been bought yet, an Intel N100 mini PC is roughly four
times the CPU and supports NVMe for about the same money. Since the B1 Pro is
already in hand, this plan uses it.

## Target architecture

- Mini PC, headless Ubuntu Server 24.04 LTS, on Ethernet, reachable over
  Tailscale.
- Foundry VTT 14.365 (same build as now), Delta Green system 2.0.1, worlds and
  modules on the SSD, listening on port 30000.
- Hermes Agent with the `ttrpg` and `extremophilia` profiles, the same
  OpenRouter model config, the same skills and external doctrine directory.
- The vendored Foundry bridge, the `ttrpg_gm` repo, the world engine, and the
  campaigns directory.
- The Mac and the iPhone become clients: a browser for Foundry, Hermex for the
  bot chat, both over Tailscale. The Mac stops running the GM stack after
  cutover, so no two gateways hold the same bot tokens.

## What actually moves

- Foundry data: 140 MB total. Systems 125 MB, modules 14 MB, the `deltagreen`
  world under 1 MB.
- Hermes profiles: `ttrpg` 644 MB, `extremophilia` 118 MB, including skills,
  sessions, and the memory files.
- Repo: 226 MB, of which `campaigns/` is 172 MB and is not tracked by git.
  `bridge/vendor` is generated by `bridge/vendor/setup.sh`, so it does not need
  to be copied.
- Cron jobs, plugins (memory provider), and the model config.

## Phase 1: hardware and OS

1. Fit the SATA M.2 SSD. Keep the eMMC as the emergency install or wipe it.
2. Install Ubuntu Server 24.04 LTS, hostname `gm`, user `chriscoon`, OpenSSH.
3. Give it a DHCP reservation on the router, or a static address.
4. Install Tailscale and join the tailnet. Confirm the Mac can reach it by
   Tailscale name.
5. Basic firewall: allow 22, 30000, 8787, and 9119 on the tailnet only.

## Phase 2: Foundry

1. Install Node 24 on the mini PC.
2. Download the Foundry VTT Linux build with your own account, unzip to
   `/opt/foundry`, and keep data at `/srv/foundry-data`.
3. Start it once with `--dataPath=/srv/foundry-data --port=30000`, open the
   web page from the Mac, and sign the license again. The license file is bound
   to the machine hostname, so a fresh signature is expected.
4. Stop Foundry. Copy the data from the Mac:
   `worlds/deltagreen`, `systems/deltagreen`, `modules/*`, and `assets/`.
5. Start it again, open the world, and confirm the journals, the dossiers, the
   actor, and the DG system version 2.0.1.
6. Install Extremophilia once the content key is redeemed on the Foundry site.
7. Write a systemd unit so Foundry starts at boot and restarts on failure.

## Phase 3: Hermes

1. Install Hermes with the official installer on the mini PC.
2. On the Mac, export the two profiles:
   `hermes profile export ttrpg` and `hermes profile export extremophilia`.
3. Import both on the mini PC. Then fix the absolute paths in `config.yaml`:
   every `/Users/chriscoon` becomes `/home/chriscoon`, including the MCP server
   command, the bridge working directory, and the external skills directory.
4. Copy `.env` secrets from the exports. Never print or paste them.
5. Verify each profile: `hermes -p ttrpg doctor`, then a one-line chat that
   reads a doctrine file and lists the Foundry tools.
6. Run the gateway as a systemd service. Keep exactly one gateway holding the
   bot tokens.

## Phase 4: bridge, repo, campaigns, engine

1. Clone `ttrpg-gm` on the mini PC. Run `bridge/vendor/setup.sh` to regenerate
   the patched bridge, then `bash bridge/check.sh`. It should report the same
   tool count as the Mac.
2. Copy `campaigns/` (untracked) and any backups you want to keep.
3. Copy or recreate the cron jobs. The engine review job is done; the status
   audit job is still useful.
4. Run the world engine's tests on the mini PC. It is stdlib Python, so this
   should pass unchanged.

## Phase 5: clients

1. Foundry from the Mac: `http://gm:30000`, or the Tailscale address.
2. Hermex: point the app at the mini PC's Hermes gateway, not the Mac's.
   If Hermex talks to the WebUI instead, run `hermes-webui` there and set
   `HERMES_WEBUI_SESSION_TTL` to a year as on the Mac.
3. Test a full turn end to end: bot chat message, Foundry tool call, journal
   read, actor read, dice.

## Phase 6: cutover and rollback

- Cutover: stop the Mac's gateway and Foundry, start the mini PC's services,
  point the clients at it, play one short test session.
- Rollback: the Mac still has its profiles, data, and repo. Stop the mini PC,
  start the Mac services, point Hermex back. Nothing is deleted during the
  migration.
- Backups: nightly rsync of Foundry data and the Hermes profiles from the mini
  PC to the Mac or an external disk, plus the repo's git remote. Keep at least
  three days.

## Gotchas, in the order they will bite

1. **SATA, not NVMe.** The M.2 slot is SATA3. Check the drive before buying.
2. **Absolute paths.** The config and scripts are full of `/Users/chriscoon`.
   A blind copy will start and then fail to find the bridge, the skills, or the
   node binary.
3. **Foundry license.** New machine, new signature. Have the license key handy.
4. **Two gateways, one bot.** Stop the Mac's gateway at cutover or Hermex will
   see the same bots twice and the bots will fight over messages.
5. **Memory provider.** The TencentDB memory plugin is the fragile piece.
   Test it early. If it will not run on the mini PC, the fallback is to run
   without it for a session and migrate the store separately, not to point two
   machines at one store.
6. **eMMC endurance.** Put Foundry data, logs, and backups on the SSD, and
   rotate logs.
7. **No browser on the server.** camofox and SearXNG stay on the Mac. The mini
   PC runs Foundry, Hermes, and the bridge only.

## Upgrade path

If the N4000 proves too slow once real play starts, the same migration moves to
an N100 or N150 mini PC with NVMe in an evening, because the data and profiles
are already portable. The hard part is the path rewrite, not the hardware.
